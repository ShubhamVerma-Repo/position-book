POSITION BOOK
=============

An in-memory trade position book service (Spring Boot 3.2.12 / Java 17) exposing
BUY/SELL/CANCEL event ingestion and position lookup over a REST API.

## How to Run

Local (Maven):
    mvn spring-boot:run
The app starts on port 8080 (see src/main/resources/application.yml). Once
running, interactive API exploration is available via Swagger UI at
http://localhost:8080/swagger-ui.html.

Testing and correctness verification:
    mvn clean verify
This is the AUTHORITATIVE correctness check for this project and is exactly what
CI (.github/workflows/ci.yml) runs on every push/PR to main. It runs the full test
suite and then enforces the JaCoCo coverage gate (85% line / 75% branch, configured
in pom.xml) - the build fails if either threshold is not met. Do not rely on
`mvn clean test` alone to judge whether the project is release-ready; only
`mvn clean verify` runs the coverage gate.

JaCoCo HTML report (generated by the above): target/site/jacoco/index.html

Docker (packaging only - see note below):
    docker build -t position-book:local .
    docker run -p 8080:8080 position-book:local
    curl http://localhost:8080/actuator/health

The Dockerfile is multi-stage: the build stage (full Maven/JDK toolchain) is
discarded entirely once it produces the jar, and only that compiled jar is
copied into a minimal JRE-only runtime image. This keeps the final image small
and free of build tooling - the same pattern used for containerized deployment
to ECS/EKS in production.

IMPORTANT: the Docker build stage runs `mvn clean package -DskipTests`, not
`mvn clean verify`. This is deliberate and explained inline in the Dockerfile: by
the time a real pipeline builds this image, CI has already run `mvn clean verify`
and passed (including the JaCoCo gate). The Docker build's only job is to package
already-verified code into a runnable artifact - it does not re-prove correctness,
and it must not be treated as a substitute for `mvn clean verify`.

## API Contract

Base path: /api/v1

1) POST /api/v1/trades/buy
   Request:
     { "id": 1, "account": "acc1", "securityId": "sec1", "quantity": 100 }
   Response: 201 Created
     {
       "account": "ACC1",
       "securityId": "SEC1",
       "netQuantity": 100,
       "events": [
         { "id": 1, "type": "BUY", "account": "ACC1", "securityId": "SEC1", "quantity": 100, "processedAt": "2026-09-22T14:00:00Z" }
       ]
     }

2) POST /api/v1/trades/sell
   Request:
     { "id": 2, "account": "acc1", "securityId": "sec1", "quantity": 500 }
   Response: 201 Created (short positions are allowed, netQuantity can go negative)
     {
       "account": "ACC1",
       "securityId": "SEC1",
       "netQuantity": -400,
       "events": [ ... ]
     }

3) POST /api/v1/trades/cancel
   Request:
     { "id": 1 }
   Response: 201 Created (returns the current position state after the cancellation)
     {
       "account": "ACC1",
       "securityId": "SEC1",
       "netQuantity": -500,
       "events": [ ... includes a CANCEL record for id 1 ... ]
     }

4) GET /api/v1/positions/{account}/{securityId}
   Example: GET /api/v1/positions/ACC1/SEC1
   Response: 200 OK, always - never 404, even if never traded (netQuantity 0, empty events)
     {
       "account": "ACC1",
       "securityId": "SEC1",
       "netQuantity": -400,
       "events": [ ... ]
     }

5) GET /api/v1/positions
   Response: 200 OK
     [
       { "account": "ACC1", "securityId": "SEC1", "netQuantity": -400, "events": [ ... ] },
       ...
     ]

All requests/responses are application/json. Validation errors, malformed JSON,
unknown JSON fields, unsupported content types (415), wrong HTTP methods (405),
and business rule violations (duplicate id, cancel of unknown/already-cancelled
event) all return a consistent error shape (see Observability section) rather
than Spring's default ProblemDetail format. 415 and 405 are named, deliberate
parts of this error contract, not incidental side effects.

Unknown JSON fields are strictly rejected (fail-on-unknown-properties=true), not
silently ignored. In a regulated financial environment, silently ignoring
unexpected fields in a request is treated as a risk rather than a convenience -
a client sending fields the server doesn't recognize should get an explicit
error, not silent data loss.

## Architecture

    controller/   TradeController, PositionController - HTTP boundary only:
                  request mapping, @Valid/@Validated triggers, status codes.
    service/      PositionBookService interface + PositionBookServiceImpl -
                  orchestrates handler dispatch and repository reads; owns the
                  getPosition() input-blank guard.
    service/impl/ BuyEventHandler, SellEventHandler, CancelEventHandler - one
                  EventHandler<T> implementation per event type; thin: normalize,
                  build a TradeEventRecord (or none, for cancel), delegate to the
                  repository, return a PositionKey.
    repository/   PositionBookRepository - the single source of truth. In-memory,
                  ConcurrentHashMap-backed. Owns all mutation and the concurrency
                  strategy (see below).
    model/        DTOs (BuyRequest/SellRequest/CancelRequest with bean validation),
                  and internal domain types (TradeEventRecord, PositionKey,
                  PositionResponse, EventType) - the repository/service layers never
                  touch the DTOs directly.
    exception/    Custom unchecked exceptions, ErrorResponse, GlobalExceptionHandler
                  (@RestControllerAdvice) - the single place reject-path responses
                  and logging are produced.
    filter/       CorrelationIdFilter - request-scoped correlation id, MDC-bound.
    util/         IdentifierNormalizer - the one place account/securityId
                  case-normalization happens.

BuyRequest/SellRequest/CancelRequest are deliberately distinct types with no
shared "type" field, supporting the three-separate-endpoints decision - which
means there is no single shared request type for one non-generic handler
interface to accept. EventHandler<T> is a generic interface with one
implementation per request type, preserving a shared Strategy-pattern contract
without forcing a fake common type or three fully unrelated interfaces.

Since Java generics are erased at runtime, Spring cannot distinguish
EventHandler<BuyRequest> from EventHandler<SellRequest> by type alone when
wiring dependencies - each handler bean is given an explicit name
(@Component("buyEventHandler") etc.) and PositionBookServiceImpl wires each in
with a matching @Qualifier. PositionBookServiceImplIntegrationTest specifically
asserts the observable effect of each method (BUY increases quantity, SELL
decreases it) rather than just checking the Spring context loads, because a
bare context-load test would not catch buyHandler and sellHandler being
accidentally wired to the wrong bean.

## Assumptions and Rationale

- Event id uniqueness: each BUY/SELL id is assumed globally unique and is the
  idempotency/duplicate-detection key. A second BUY/SELL with the same id is
  rejected (DuplicateEventException, 409) rather than silently merged or
  overwritten - trade ids are typically assigned upstream (e.g. by an OMS) and
  should never collide in a correct client.

- Short positions are allowed: SELL is never blocked by insufficient prior BUYs.
  netQuantity can go negative. This matches the standard real-world convention
  where a negative position quantity represents a short position, not an error
  state.

- CANCEL is terminal: once an event is cancelled it cannot be cancelled again
  (InvalidEventException, "already cancelled"), and a CANCEL record itself can
  never be cancelled (it is never stored in eventsById in the first place, so
  attempting to cancel a CANCEL's id falls through to EventNotFoundException,
  404). This mirrors the FIX protocol precedent where OrdStatus=Cancelled is a
  terminal state with no further transitions defined.

- Double-cancel is rejected, not idempotent: a second cancel attempt on the same
  id is treated as an invalid state transition (409-class error, InvalidEventException)
  rather than silently succeeding a second time, because a second cancel almost
  always indicates a client-side bug (retried request without idempotency
  protection, or a logic error) that should surface loudly rather than be masked.

- A never-traded position returns 200 with netQuantity 0 and an empty events list,
  not 404. The actual alternative considered was inferring account validity from
  whether the account had appeared in ANY prior trade event at all (not just this
  specific account/security pair), returning 404 only for accounts never seen
  anywhere. This was rejected because: it cannot distinguish a brand-new,
  legitimate account with zero trades ever from a genuinely invalid/typo'd
  account, since both look identical as "never seen"; it produces inconsistent
  semantics, since two accounts in an equivalent "no position here" state would
  get different HTTP treatment purely based on unrelated trade history elsewhere;
  and it doesn't actually solve account validation in the first place, since a
  typo'd account that happens to have traded something else previously would
  still pass through undetected. Treating "never traded" as an error
  would require either a separate reference-data source (out of scope) or an
  arbitrary allowlist, neither of which the spec provides. Zero-state-by-default
  is simpler, matches how most position/inventory systems behave, and avoids the
  service silently disagreeing with itself (a position that legitimately nets to
  zero after being fully unwound looks identical to "never traded" - both should
  return the same 200 zero-state, not diverge into 404 vs 200 based on history).
  PositionNotFoundException and its GlobalExceptionHandler mapping are kept in the
  codebase as a deliberate extension point in case a future stricter-lookup
  variant is needed, not as dead code.

- Three separate endpoints (buy/sell/cancel) rather than one unified "submit
  event" endpoint: this is deliberately stronger than a single endpoint accepting
  an event-type discriminator field, for several reasons - each endpoint has its
  own precise request shape validated by bean validation with no polymorphic
  payload or type-discriminator parsing; the EventHandler<T> per type keeps each
  handler trivially unit-testable in isolation with no branching on event type;
  and it makes the OpenAPI/HTTP contract self-documenting (three named operations
  with three named schemas, rather than one endpoint whose valid body shape
  depends on a field's value).

- Case normalization is centralized in IdentifierNormalizer (trim + uppercase),
  invoked exactly once per request path (in each EventHandler and in
  PositionBookServiceImpl.getPosition), never duplicated inline elsewhere. The
  repository explicitly assumes its inputs are already normalized and does not
  re-normalize - this is stated in its Javadoc so there is exactly one place in
  the codebase responsible for normalization and no ambiguity about whose job it
  is.

- Quantities are whole numbers only (Long), matching @Positive/@Max(1_000_000_000)
  validation on BuyRequest/SellRequest. Fractional share quantities are out of
  scope; the domain here is treated as whole-unit trade quantities.

- Path-variable validation: PositionController's {account}/{securityId} path
  variables are constrained with @Pattern (alphanumeric only) and @Size bounds,
  mapped to 400 via ConstraintViolationException. @Validated must be present at
  the controller class level for Spring to actually enforce constraints on a
  bare @PathVariable - without it, these annotations are silently ignored rather
  than erroring, which was specifically tested for and caught during
  development.

## Concurrency and Data Integrity

PositionBookRepository is the only place mutation happens, and every mutating
operation (recordBuyOrSell, cancelEvent) is a single `synchronized` method that
performs its full check-then-act sequence atomically: duplicate-id check + store
in one method body, not-found/already-cancelled check + reversal + cancel-record
in the other. No public "check" method (findEvent, isCancelled, eventExists) is
ever meant to be called by an external caller as the basis for a subsequent
mutating decision - doing so would reintroduce a race between the check and the
act, even if each method were individually synchronized, because another thread
could interleave between the two calls. This is documented directly in the
repository's Javadoc and on each read-only method.

This exact race was caught during design, not left to be discovered later - an
earlier design considered exposing eventExists() and recordEvent() as separate
repository calls for a handler to use in sequence, which was rejected
specifically because two concurrent requests could both pass the existence
check before either recorded its event, silently double-accepting the same
event id. The current atomic recordBuyOrSell/cancelEvent design is verified
under real thread contention by two dedicated concurrency tests in
PositionBookRepositoryTest: one spins up 20 real threads racing to record the
same event id simultaneously (CountDownLatch-coordinated start, run across 10
independent iterations for reliability) and asserts exactly one thread succeeds
while the other 19 receive DuplicateEventException; the other spins up 50
threads with distinct event ids on the same position and asserts no lost
updates under contention (also across 10 iterations). Both were verified stable
across three separate `mvn clean verify` runs with no flakiness.

A single lock (the repository instance itself) is simple to reason about and
correct at the current scale - every mutation touches a handful of maps and
completes quickly. The natural next step at higher throughput would be
per-position lock striping (one lock per PositionKey) so unrelated positions stop
contending on a single monitor, but that adds real complexity (lock management,
avoiding deadlock across any future multi-position operation) that isn't
justified until contention on the single lock is actually observed.

Overflow protection is two-layered: BuyRequest/SellRequest.quantity is capped at
@Max(1_000_000_000) at the DTO boundary, and independently every net-quantity
mutation inside the repository goes through Math.addExact/Math.negateExact (never
raw + or -), which throws ArithmeticException on overflow rather than silently
wrapping. The DTO cap means true overflow cannot be reached through the public
HTTP API today, but the repository-level guard exists as defense in depth and is
verified directly (bypassing DTO validation) in PositionBookRepositoryTest.

Event history is append-only and immutable: TradeEventRecord has no setters, all
fields are final, and each position's drilldown list is a CopyOnWriteArrayList
that is only ever appended to, never rewritten or removed from. Callers only ever
receive defensive copies (List.copyOf) via PositionResponse, never live references
into repository state. processedAt is always server-assigned via Instant.now() at
the moment a TradeEventRecord is constructed - it is never accepted as client
input (no request DTO has such a field), so the audit trail's timestamps cannot
be backdated or otherwise tampered with by a caller.

## Observability

Every request is assigned a correlation id (CorrelationIdFilter): the incoming
X-Correlation-Id header is used if present and non-blank, otherwise a UUID is
generated. The id is placed in SLF4J's MDC under "correlationId" for the duration
of the request (cleared in a finally block, so a reused container thread never
leaks a stale id into the next request) and echoed back in the response header.
logback-spring.xml's console pattern includes [correlationId=%X{correlationId}]
on every log line so all logs for a single request can be grepped together. This
filter also runs on Actuator's /actuator/health requests with negligible overhead
(a header read/generate and an MDC put/remove, no I/O).

Logging is split cleanly by boundary: each EventHandler (Buy/Sell/Cancel) logs
exactly one INFO line on successful acceptance (event id, account, securityId -
never the raw request body or any other payload). GlobalExceptionHandler is the
single place reject-path logging happens (WARN for all 4xx/405/415 mappings with
the exception message, ERROR with full stack trace for the generic 500 fallback -
the stack trace is logged server-side only and never included in the response
body). Handlers deliberately do not log failures themselves, to avoid duplicate,
confusing log lines for the same rejected request.

## Test Coverage

The coverage gate is enforced (mvn verify fails below threshold), not merely
reported, because the exercise's "full and high quality test coverage"
requirement is a concrete guarantee only if unmet coverage can actually block a
release - a report alone is just a claim.

Final JaCoCo numbers (mvn clean verify): 98.1% line coverage (258/263), 100%
branch coverage - both comfortably above the enforced 85% line / 75% branch
gate in pom.xml, confirmed stable across three separate mvn clean verify runs.
target/site/jacoco/index.html has the full file-by-file breakdown.

Three tests are deliberately not end-to-end HTTP tests, and each is a genuine,
non-gaming exception documented at the point of use:

  - PositionNotFoundException: no real call path in the app throws it today (see
    "never-traded returns 200" above) - it is a deliberate extension point, not
    dead code. GlobalExceptionHandlerTest verifies its mapping by invoking the
    handler method directly with a constructed exception instance, which still
    exercises real production code, just without a currently-nonexistent trigger.

  - ArithmeticException overflow: BuyRequest/SellRequest's @Max(1_000_000_000)
    validation makes true end-to-end overflow through the HTTP API impossible.
    PositionBookRepositoryTest proves the repository's Math.addExact guard fires
    by calling recordBuyOrSell directly (bypassing DTO validation, which is
    legitimate whitebox testing of the repository itself), and
    GlobalExceptionHandlerTest separately verifies the 400 mapping.

  - Generic Exception -> 500 fallback: nothing in the current codebase throws an
    exception type without a specific handler, so there is no way to trigger this
    via HTTP without injecting an artificial failure. GlobalExceptionHandlerTest
    invokes the handler method directly instead.

No test was written solely to inflate the coverage number; every test in the
suite (including these three) asserts genuine, meaningful behavior of real
production code.

## Out of Scope

- AuthN/authZ: no authentication or authorization is implemented. Every endpoint
  is open. Adding this was not part of the given scope.
- Idempotency keys for retried requests: duplicate detection exists only via the
  client-supplied event id (see Assumptions). There is no separate
  idempotency-key/response-caching mechanism for safely retrying a request whose
  response was lost in transit.
- Multi-instance / distributed state: storage is entirely in-memory
  (ConcurrentHashMap-backed) and local to a single JVM instance, per the given
  constraint. There is no shared/distributed state, replication, or persistence -
  restarting the process or running more than one instance behind a load balancer
  would each see an independent, empty book.
- Out-of-order event buffering: events are processed strictly in arrival order;
  there is no reordering, buffering, or sequence-gap detection for events that
  arrive out of their logical/business order.
- Structural limitation - account/securityId containing a literal "/": the GET
  /api/v1/positions/{account}/{securityId} endpoint binds account and securityId
  as individual path segments. A value containing a literal "/" cannot be
  represented in that path shape (it would either 404 as an unmatched route or
  split into extra path segments) - this is a structural limitation of
  path-variable-based routing, not a validation gap. The @Pattern constraint
  (alphanumeric only) additionally rules out "/" and other special characters
  from valid account/securityId values in the first place, so this only matters
  if that constraint were ever relaxed.

## Dependency Security Notes

pom.xml pins Spring Boot 3.2.12 (the latest patch on the 3.2.x line, chosen
deliberately over jumping to 3.3.x/3.4.x to minimize behavioral risk this late
in the project) and overrides three of its managed dependency versions via
properties, each verified individually against Maven Central and re-tested
with `mvn clean verify` (all 68 tests, 85%/75% coverage gates) plus a Docker
build/run/health-check after each change:

- tomcat.version -> 10.1.55 (parent manages 10.1.33, which is in the
  vulnerable range for CVE-2025-31650, CVE-2025-52520, and CVE-2025-55668;
  10.1.55 is past all three fixed-in versions)
- spring-framework.version -> 6.1.21 (parent manages 6.1.15; 6.1.21 is the
  latest version of the 6.1.x line published as open source on Maven
  Central, resolving CVE-2025-22233 and CVE-2025-41234)
- logback.version -> 1.5.19 (parent manages 1.4.14; 1.5.19 resolves
  CVE-2024-12798 and CVE-2025-11226 - the project's logback-spring.xml uses
  only a ConsoleAppender and a plain pattern, no Janino/EvaluatorFilter or
  conditional `<if>` processing, so neither CVE was ever exploitable here,
  but the version is still patched for defense in depth)

Known limitation, deliberately not chased further: CVE-2025-41242 (fixed at
Spring Framework 6.1.22) and CVE-2025-41249 (fixed at 6.1.23) have no
open-source fix available on the 6.1.x line - 6.1.22/6.1.23 exist only under
VMware Tanzu's commercial support subscription and are not published to
Maven Central. The first version of Spring Framework with an OSS fix is
6.2.10/6.2.11, which Spring Boot does not pull in until 3.4.0 (verified
directly: Spring Boot 3.3.13, the latest 3.3.x patch, still manages
spring-framework.version 6.1.21, the same version this project uses).
Reaching 3.4.x would mean leaving the 3.2.x line entirely, which was
explicitly ruled out for this project to avoid late-stage behavioral risk.
This gap is accepted as-is rather than worked around with an unsupported
cross-line framework override.
